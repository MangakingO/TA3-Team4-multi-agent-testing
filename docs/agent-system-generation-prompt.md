# Prompt used to generate the agent system (What To Do, item 3)

The agent system was generated by **Claude (Opus 5.5) on claude.ai**, with the assignment PDF and
`SeasonSwitch.java` attached. The prompt below consolidates the requirements given to Claude during that
conversation into one prompt, so it can be read on its own and reused. The first version was generated in
Python; when the course asked for Java, Claude rewrote the whole system in Java with the same design (this
prompt includes that requirement). After generating the system, the team reviewed, debugged and tested it
(What To Do, item 4).

---

**Role.** You are a senior Java engineer who builds LLM agent systems with LangGraph4j and LangChain4j, and
an experienced Java test engineer.

**Context.** The attached PDF is our assignment (CSE 4392/5320, Team Assignment 3). The attached
`SeasonSwitch.java` is the class under test. Our team runs models locally with **Ollama**.

**Goal.** Write a multi-agent system in **Java** that tests `SeasonSwitch.java` and refactors it with the
**State pattern**, following the 12 steps of the assignment in order. The test cases are JUnit 5 tests and the
refactored code is Java.

**Technology**
- Java 17, Maven, one runnable jar (`java -jar target/ta3-agents.jar ...`).
- LangGraph4j for the orchestration: a `StateGraph` with a typed state, parallel branches, conditional edges,
  SQLite checkpoints (`SQLiteSaver`), and interrupts for the human in the loop.
- LangChain4j `OllamaChatModel` with a local model (default `qwen2.5-coder:7b`). Agent outputs are JSON:
  send the JSON Schema as Ollama's structured-output format and validate the reply into Java records.
- JUnit 5, JaCoCo (branch coverage), javap, all run through Maven.

**Architecture**
1. One graph node per step. The process is fixed, so routing is deterministic (conditional edges). Use an
   LLM only where judgment is needed: an EP agent, a BVA agent, a reviser, a repair agent, a coverage agent,
   a refactoring agent and a test adapter.
2. Steps 1 and 2: the EP and BVA agents run in parallel (fork, each on its own thread) and join before step 3.
3. Step 3: a deterministic curator removes duplicates. Two tests are duplicates if their code is the same
   after normalizing local variable names (string literals are test data and must be kept), or if they have
   the same method, input and expected result. Show conflicts to the reviewer.
4. Steps 4 and 9: human in the loop. The node interrupts the graph at its last checkpoint; the person accepts
   or requests changes in plain words; the run can be resumed later or from another terminal (answer files).
5. Steps 5, 6 and 10: run the tests with `mvn test` and parse the Surefire XML. A repair agent decides
   whether the code or the test is wrong, makes the smallest fix, and every change is logged (who, why,
   unified diff) in `changes.md`. Loop until all tests pass; at a limit, a person decides.
6. Steps 7, 11 and 12: read JaCoCo's XML. If branch coverage is below 100%, a coverage agent writes tests for
   the branches never taken (give it the source with the missed lines marked).
7. Step 8: the refactoring agent uses the team's final prompt from a file. Check the result by compiling it
   and inspecting the bytecode with javap: abstract State, concrete states, delegation, no `switch` on the
   state, the same public interface.
8. Step 10: reuse the accepted tests. Adapt the ones that no longer compile, or delete the ones that only
   tested an implementation detail the refactoring removed, giving the reason.
9. Save the test cases (JSON and Markdown), the test results and the coverage reports for the original and
   the refactored code separately, plus a summary.

**Testability.** SeasonSwitch prints to `System.out`, uses `javax.swing.Timer`, keeps its state in a static
field, and its `main()` calls `System.exit` or waits forever. Provide a JUnit helper that captures the output,
stops the timers after each test, resets static fields, and runs `main()` in a separate JVM that carries the
JaCoCo agent so its coverage counts. Analyze the class automatically and give these facts to the agents in
their prompts.

**Prompts.** Keep every agent prompt in its own Markdown file with SYSTEM and USER sections and
`$placeholders`. Include the JSON Schema and ask for JSON only.

**Also provide:** a command-line interface (run, resume, status, report, list, lab, graph); a manual LLM mode
that writes each prompt to a file so a web LLM can answer it; a prompt lab that scores versions of the
refactoring prompt (compiles, pattern checks, tests reused, coverage); a trace of every step and every prompt
and reply; a README; and JUnit tests that drive the whole graph with a scripted model on a small stand-in
class through real Maven, JUnit and JaCoCo runs.

**Output.** The complete Maven project, file by file, then how to build and run it on Windows and macOS.
